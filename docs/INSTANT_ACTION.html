Instant Action: plan

A menu-driven "pick a lance, pick a map, drop" web app over the btlib10x engine, built on the repo's TUI kit, with a vector hex map. Draft plan, revision 4 (2026-10-25), written against main at aa4d6080. Revisions 2 to 4 apply inseok's answers: no command input, no code shared with the terminal, the vector map viewer for the board, TW deployment, two victory modes and a separate i18n.

1. Summary and decisions

  • What: a new page, web/instant.html, with an Instant Action flow in the MechWarrior sense: pick 'Mechs and pilots for two sides, pick a map and a victory mode, deploy, fight, read the debrief, rematch.
  • No text commands. Every terminal command has a TUI equivalent: menus, lists, checkboxes, radio groups and dialogs. Fire, for example, is a table of the fireable candidates with a checkbox per weapon.
  • Board: the canvas renderer from map_viewer_vector.html (hex prisms, free rotation, view tilt, elevation to scale), extended with terrain fills, overlays and upright unit "banners" drawn in Bt10x Mono glyphs. Hexes are picked by mouse click only; everything else is reachable by keyboard.
  • Dependencies: only the engine bundle (web/btlib10x.js, imported as "btlib10x") and the TUI kit (web/tui.js, web/tui.css). Nothing is imported from web/terminal/; the pieces worth keeping (persona AI, RNG, victory check, undo snapshots, event wording) are copied into web/instant/ and adapted.

3. UI library: TUI kit and prefabs

The repo's own kit, web/tui.js + web/tui.css (docs/TUI.md), is the "tui prefab": TUI.prefab(name, defaults, render) registers a template, TUI.h.use(name, props) instantiates it and TUI.mount(target, node) renders a scene whose update() diffs and keeps focus, scroll and selection. It already has the parts this app needs: window, dialog, split, tabs, menu, list, menubar, table with row select, checkbox, radio, select, progress, scrollbox, status bar, tooltip. It costs no new dependency and is already in dist:web.

Small additions the app needs

  • Checkbox table rows for the fire panel: a table whose first column is a check and whose rows can be disabled with a reason. Built as an app prefab first; moved into the kit only if the demo page wants it.
  • Screen keymap with a modal stack (hotkeys that work wherever focus is). App code in web/instant/keys.ts.
  • Fixed screen: the 100×32 fit-and-centre logic (§8.0) in web/instant/screen.ts, setting --tui-fs.
  • Raw slot for the map canvas: a pane marked data-tui-raw so the kit does not touch its content.

Turn controller

  1. controller.ts runs gameLoop(state, rng, stopper, sink). It returns the next actor, or stops on victory.
  2. If the actor has a persona, the controller calls ai.decide() and applies its Action[] through the same path a human uses. AI pacing (instant / one activation per key / timed) only changes when the log and map catch up.
  3. Otherwise the HUD opens the actor's orders panel and waits. Every UI interaction is an Action; commit actions call the engine and loop back to 1.
  4. Before each commit the controller pushes an undo snapshot; a thrown engine error restores the snapshot and shows the message in a dialog (the same guarantee the terminal gets from commitAtomic).

6. Map view: vector hex + banner glyphs

What is kept from the vector viewer

  • Regular flat-top hexagons on the btlib10x odd-q offset grid (even columns half a hex south), drawn on a canvas, opaque faces painted back to front, every edge stroked once.
  • Free rotation by dragging the map, snapping in 60° steps from the keyboard; view tilt (default about 40°, 90° = straight down); elevation to scale (a level is 6 m on a 30 m hex), with walls drawn only where they face the viewer.
  • Coordinate labels CCRR, lying flat on the face along the edge nearest the screen top: off by default, shown only on the hovered hex (MapView.showCoords turns them on for every hex).
  • HUD: a north indicator at the top right; at its top left the view state (⟲ rotation, × zoom against fit, ⦟ tilt) in the N's colour, double size, outlined in black. The indicator has its own mouse controls (nothing under it is hovered or picked): left click turns back to north-up, middle click fits the map to the canvas at the current angle and tilt, right click turns +60° (Shift+right click −60°, exact, no snapping), the wheel steps the tilt by 5° between 5° and 90° (TILT_MIN / TILT_MAX / TILT_STEP in view.ts). The browser menu is suppressed over the indicator only.
  • Fit to canvas (the default zoom, Home, and the indicator's middle click) uses the projected extent of every hex corner on the ground and at its level, so the map is centred exactly at any angle and tilt; headroom is added above only for banners that stick out of the top of the map.
  • Polygon hit testing (hexAt(px, py), last-drawn first), reused for clicks.

8. Screens, layouts and menus

8.0 Screen size: 100×32, centred, fixed font

Like a DOS text mode, the application lives in a fixed grid of 100 columns × 32 rows: 31 rows of window and 1 status-bar row. Every screen and every mockup below uses exactly that grid; modal windows are smaller and sit centred on it.

  • Font size. The grid never reflows, and the font size is the player's: whole px from 10 to 40, set with the header's A− / A+ buttons (readout between them) and Fit, kept in localStorage (bt10x.ia.fontSize, every access guarded). Resizing the window never changes it, so glyphs keep their size; browser zoom scales the page as on any web page. Fit picks, once, the largest size where the whole grid fits the space between header and footer (TUI.fitFontSize: floor(min(w / (100 × cw/fs), h / (32 × ch/fs))) from the measured cell). A first visit starts at the Fit size, fitted again after document.fonts.ready, and keeps it. The kit's auto-fit (TUI.autoFit, re-fit on every resize) stays off here.
  • Centring. The screen is centred horizontally; a window narrower than the screen clips both sides equally and never scrolls sideways (#stage-inner, overflow-x: clip). Vertically it is middle-aligned while it fits and otherwise starts at the top with the stage scrolling down (margin-block: auto, so nothing is lost above). The space around it is page background, as the black border around a DOS screen. Open popups and tooltips close when the stage scrolls.
  • Map pane. The canvas fills its pane's cell rectangle exactly; map zoom is separate from the font size, and the map's own fit-to-pane zoom is the default. A font change scales a hand-set map zoom and pan by the same factor, so the framing stays.
  • Small screens. No notice: the player lowers the size or uses Fit; what still doesn't fit is clipped at the sides or scrolls. A reflowing phone layout is out of scope for v1.

10. Deployment and victory rules

10.1 Starting positions (TW p. 256)

TW's scenario set-up: both players roll 2D6; the higher result chooses a home map edge and the opposite edge becomes the opponent's. All units start off the map and may enter on any hex along the home edge, regardless of terrain, provided the unit can legally enter it; the entry hex counts as the first hex of movement. Initiative for turn 1 is rolled normally.

TW ruleInstant Action
2D6 roll-off, winner chooses home edge, loser gets the oppositeAs written, rolled with the battle seed's set-up stream (salted apart from the battle dice, like the terminal's pp setup); ties re-roll. Edges: North (row 1), South (last row), West (column 1), East (last column).
Units start off the map and enter along the home edgeThe engine has no off-map units. v1 places each unit on a home-edge hex before turn 1, facing into the map (deployment screen). Only hexes the unit could legally enter are offered; one 'Mech per hex.
The entry hex counts as the first hex of movementHouse rule (decided): the first placement is free. Each unit starts on its home-edge hex and pays nothing for entering it; its first movement starts from there.
Leaving by the home edge = retreat; other edges = destroyed (p. 257)Not modelled: the engine keeps units on the map. Withdraw (F9) ends the whole battle instead.

10.2 Engagement modes

ModeEndsWinner
Annihilation (Standup Fight, TW p. 259)When one side has no unit left in play (destroyed, or removed: ejected, killed, abandoned hull); the copied checkSessionVictory logic.The side with units left; both gone at once is a draw.
Attrition (turn limit N, default 10, range 3–30)At the end of turn N (after the heat and end phases), or earlier if Annihilation's condition is met.The side that dealt more damage. Ties go to the higher scoreReport score, then a draw.

Damage dealt by a side = the armor and internal structure points the opposing side's units have lost since the battle started, read from unit state (start totals from the resolved MechDef, current from unit.damage). It counts every source that hit the enemy (weapons, physical attacks, falls, ammo explosions). A destroyed location counts all its points; a destroyed unit, and a unit left as a hull (pilot ejected, killed or abandoned), counts its whole armor + structure total (decided, §16). It needs no new engine event, and it is the same number the debrief shows. Both stoppers are passed to gameLoop; the engine never decides the winner (docs/VISION.md: victory belongs to the caller).

The battle header shows the mode: Attrition · turn 5/10 · 132 : 96. The names are the app's own (TW p. 257 has no named modes); the code keeps the ids destroyAll / damageRace, which saved loadouts use.

13. i18n

  • Own catalog: web/instant/i18n/en.ts (canonical) and ko.ts, compile-checked against en the same way the terminal's catalogs are, with kr accepted as an alias. No keys are shared with web/terminal/i18n.
  • Locale choice follows the site convention: ?lang=, then localStorage["bt10x.lang"], then English, so the landing page, terminal and Instant Action stay in step.
  • Scenes take their strings through TUI.h.t(key) backed by this catalog (registered with TUI.i18n.add), so a language switch re-renders every scene.
  • Engine messages (thrown errors, GameEvent text) stay English, as in the engine. The log formats events itself from their structured fields, so log lines are localized; raw engine error text is shown in dialogs with a localized heading.
  • Persona names and trace terms get Instant Action keys.

The app loads three packs at boot: base and SW (as the terminal does) and the Instant Action map pack via appendCatalog(text, "ia"). A failed SW or IA fetch degrades with a warning. Stale-dist trap applies: web/instant typechecks against dist/, so run npm run build after engine changes.

A Biome rule (or a test) enforces the boundary: no import path under web/instant/ may reach web/terminal/.

Tests

Logic stays DOM-free (setup, battle, ai, log, map geometry) so vitest covers it. One new area file, tests/instant.test.ts:

  • Deployment: roll-off is seed-stable; offered hexes are on the chosen edge, legal to enter and unoccupied; auto-placement never stacks.
  • Actions: every terminal command form has an Action that the controller accepts in the matching phase, and an illegal one leaves state unchanged (undo snapshot restored).
  • Same seed, same battle: a scripted battle played through Actions ends in the same state as the terminal session playing the equivalent commands (the test may import both; the boundary rule applies to app code only).
  • Victory: Annihilation and Attrition end on the right turn with the right winner; the damage tally matches a hand-computed case; ties fall through to the BV score.
  • AI: a full all-persona Random battle with a fixed seed reaches the debrief.
  • Map: hit testing returns the clicked hex at 0°, 60°, 240° and several tilts, including elevated hexes.
